= image-rota

== Immutable root and mount points

This system uses an A/B, read‑only root with all writable state on a single persistent partition.

[cols="1,3,1,4", options="header"]
|===
| Mount point | Backing | Type | Notes

| / | /dev/disk/by-slot/active/system | erofs or ext4 | ro System root (active slot A or B)
| /boot/firmware | /dev/disk/by-slot/active/boot | vfat | ro Boot files (active slot A or B)
| /bootfs | BOOTFS | vfat | rw Boot metadata
| /persistent | PERSISTENT | ext4 | rw Shared persistent storage
| _(not mounted)_ | /dev/disk/by-slot/<name> | ext4 | Optional private partition, see <<private-partition>>
|===

The persistent mount point is set by `IGconf_image_persistent_dir` (default `/persistent`). The partition is checked and mounted in the initramfs.

* **Rationale (immutable root + A/B)**
   ** Supports delta/incremental OTA updates by treating root as a static image.
   ** Reliable rollbacks: slot can be flipped if a new root fails health checks.
   ** Reduced write amplification and storage wear, clearer separation of state.
   ** Preserves SBOM accuracy: executing software matches the manifest exactly.
   ** Blocks on-device package installs, preventing SBOM drift.
   ** Enables auditable, reproducible releases and stronger supply-chain assurances.

State on the persistent partition is handled by layer `slot-state`.


[[private-partition]]
== Private partition

`image.private_part_name` adds one more partition between `system_b` and `persistent`. It holds an empty ext4 filesystem labelled with the name in capitals, sized by `image.private_part_size`. The boot partitions keep numbers 2 and 3, and `persistent` stays last, so it can still grow to the end of the device.

The system does not mount it. It is meant for a single service that mounts it in its own mount namespace, for example with `PrivateMounts=yes`, and finds it as `/dev/disk/by-slot/<name>`. That keeps its contents out of the filesystem every other process sees, and independent of how full `/persistent` is or whether it gets reformatted.

Like every partition it arrives only with a new installation: an update replaces the slots, never the partition table. The provisioning map gets an entry for it with `pmap: clear`; the encrypted maps do not support it yet.

With `image.private_part_fs: none` it ships without a filesystem, so that its service formats it on the device with the device's own defaults rather than the build's. genimage then gets a file of the partition's size that is all hole: it stays a hole in the disk image, becomes "don't care" in the sparse image, and nothing is written to the partition on installation. The service has to format an empty partition itself, and should leave alone one that holds anything else.

[[reserve-partition]]
== Reserve partition

An update cannot change the partition table, so a layout that turns out too small needs a new installation of every device. `image.reserve_part_size` keeps space for that: a partition named `reserve` in front of `persistent`, after the private partition if there is one, without a filesystem and never mounted. Its content is undefined. Like the raw private partition it is all hole in the images, so an installation writes nothing to it.

A later update can take space from it while the system runs, since nothing mounts it: shrink the `reserve` entry and create a new partition next to it, or let the private partition in front of it grow into it. Because `persistent` stays last, it still grows to the end of the device. The provisioning map gets an entry for it with `pmap: clear`.


== Slot Selection (run-time)

Handled entirely by layer `rpi-ab-slot-mapper`.

== Slot Pairing (build-time)

=== Definition

This layer generates an image which has bit-for-bit identical A/B slot members:

- Both `a.boot` and `b.boot` contain the exact same vfat filesystem.
- Both `a.system` and `b.system` contain the exact same ext4 filesystem.
- Filesystem UUIDs are intentionally identical across slots.
- GPT partition GUIDs (PARTUUID) are unique per partition.
- GPT partition labels (PARTLABEL) are unique per partition.

=== Rationale and benefits

- Faster image creation: only a single slot pair is produced.
- Simpler updates: only a single slot pair is built, tested, and distributed.
- Update generation: operating on a single slot pair is unambiguous.
- Smaller CI/storage footprint: fewer images to store.

=== Requirements and constraints

- Does not use `UUID=` anywhere. Duplicate filesystem UUIDs make `/dev/disk/by-uuid/*` ambiguous.
- Uses stable identifiers instead, e.g. `/dev/disk/by-slot/{active,other}/{boot,system}`.

=== Encrypted (LUKS) Provisioning Map layouts

- Identical content inside LUKS is supported. Slot mapping can use GPT labels or static map triplets to identify `mapper:<name>:<part>` slot components.
